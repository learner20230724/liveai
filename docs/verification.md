## Browser upload congestion and route disclosure — web 3.0.1, 2026-11-05

The owner reported “网络上传拥塞，已结束会话，请重试。” and confirmed using the desktop website. That exact message exists only in the browser LiveSession microphone callback; the shipped Android native service does not contain it. The browser connects to this host's authenticated `/liveai/api/live` gateway, so microphone/camera/screen data are relayed. The APK's native microphone/camera connect directly to MOSS; Android screen sharing has not been implemented. The previous UI did not make this distinction prominent enough.

A reproducible local cause was found: the old screen sender accepted a JPEG whenever the pre-send queue was below 128,000 bytes, without considering the JPEG's own size. One high-entropy screen frame could therefore push the queue above the microphone's threshold and immediately terminate the session. This reproduces the reported message but does not prove the cause of that specific owner session or locate a fault at the provider.

Browser frames now adapt JPEG quality and dimensions (camera ≤480 px, screen ≤960 px), with an enforced 32 KiB frame limit and an 8 KiB pre-send queue check. The check repeats after asynchronous encoding, so stale/disabled media cannot send late. Audio has a separate bounded 64 KiB queue; brief congestion drops stale input/snapshots instead of immediately ending the call. A continuously blocked microphone for ten seconds ends with an explicit browser-to-hub queue message, not an attribution to the provider. Camera and screen alternate if one source would repeatedly crowd out the other. Webcam/screen frames remain snapshots, and quality/frame rate can drop under load.

The live page and top bar now explicitly label browser relay, describe APP camera/voice direct mode, and state that APP screen sharing is unavailable. APP settings repeat this capability boundary. No native change or new APK is required: the website and APP web resources publish together as 3.0.1.
